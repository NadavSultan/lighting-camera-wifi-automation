# Phase 7 planning contract — reporting and export package

Contract prepared: 2026-09-03

Status: **IMPLEMENTATION COMPLETE — AWAITING INDEPENDENT QA**

Phase gate: decisions `P7-D01`–`P7-D15` were approved on 2026-09-03; implementation was separately authorized and executed on 2026-09-04. Independent QA, master gate, and seal remain pending.

## Objective

Add a safe, deterministic reporting workflow that converts one current project into clearly separated customer data, user configuration, calculated results, recommendations, warnings, assumptions, validation findings, and provenance. The workflow should produce a portable reporting package suitable for engineering review without presenting conceptual Phase 4-6 outputs as professionally validated, RF-verified, compliant, optimal, or installation-ready.

Phase 7 completes the approved product roadmap. Later user-requested fixes, usability improvements, and new features remain separate post-roadmap work and must use their own scoped contracts or issue records.

- Accepted base: `8a177b7398e167ac0a925484a577c9c85deb1806`; Phases 1-6 are closed and sealed.
- Current product/API versions: project `2.6.0`, software/API `0.6.0`, CAP model `jnet1-graph-planning-1.0.0`.
- Existing exports are portable project JSON and an updated KML limited to the accepted pole/fixture-edit contract. The updated KML intentionally contains no CAP data.
- Current project collections already separate source, user edits/configuration, camera geometry, lighting calculations, conceptual Wi-Fi results, CAP calculations/recommendations, warnings, assumptions, and provenance.
- No report-package service, XLSX/PDF writer, report manifest, report preview, or Phase 7 endpoint/UI exists.

- `README.md` remains historically stale and must be refreshed only inside an authorized Phase 7 documentation boundary.

## Approved dependencies and implementation-policy decisions

The user explicitly approved every decision below on 2026-09-03. They are binding for future Phase 7 implementation but do not authorize implementation.

| ID | Approved policy | Reason / boundary |
|---|---|---|
| P7-D01 | Produce one `.zip` package containing a manifest, project JSON archive, derived engineering KMZ, CSV schedules, XLSX workbook, PDF summary, and presentation-model JSON. Individual downloads are views of the same canonical model. | One auditable artifact with hashes avoids mismatched exports. |
| P7-D02 | Keep the existing `*-updated.kml` behavior unchanged and CAP-free. Put derived camera/lighting/Wi-Fi/CAP layers only in a separately named engineering KMZ with explicit conceptual/derived labels. | Preserves the accepted source/edit export contract. |

| P7-D04 | Define schedules for project/source inventory, poles/fixtures, cameras, lighting, Wi-Fi, CAP, warnings/assumptions, validation findings, and provenance. Empty subsystems remain visible as `not configured` or `not calculated`. | Makes completeness and absence distinguishable. |
| P7-D05 | Add pinned backend dependencies `XlsxWriter` for XLSX and `ReportLab` for PDF after dependency/security/license review. Do not use office automation or external conversion services. | Neither required writer exists today; deterministic local generation is required. |
| P7-D06 | Generate the PDF from repository-owned layout code with a cover, integrity summary, inventory, subsystem summaries, validation/limitations, provenance, and a deterministic local vector overview without an online basemap. | Avoids browser-print and network dependence. |
| P7-D07 | Treat `presentation-model.json` as structured future presentation input only; do not generate PPTX or claim presentation support in Phase 7. | Matches the roadmap wording while keeping scope bounded. |
| P7-D08 | Add `report-manifest.json` with versions, project/source hashes, generation timestamp, report-input fingerprint, included/omitted sections, warnings, and SHA-256/size for every member. | Provides integrity and reproducibility evidence. |
| P7-D09 | Add project schema `2.7.0` and software/API `0.7.0` only for strict report preferences and last-report metadata; generated bytes remain transient and are never embedded in runtime projects. | Keeps preferences auditable without bloating project state. |
| P7-D10 | Use synchronous bounded generation through `POST /api/projects/{project_id}/reports/package`, returning bytes only after full validation. Failures persist nothing. | The accepted 74-pole workload does not justify a queue/database. |
| P7-D11 | Proposed caps: 50 MiB package, 25 MiB/member, 250,000 tabular rows, 100,000 KML features, 20,000 PDF table rows with summarized overflow, 100 sheets, sanitized unique 31-character sheet names, and 2,000 characters/cell. Boundary+1 fails atomically. | Prevents unbounded generation; values require explicit approval. |
| P7-D12 | Spreadsheet cells beginning with `=`, `+`, `-`, or `@` are literal text; filenames/ZIP paths are sanitized; XML/PDF text is escaped; no macros, hyperlinks, external images, embedded source uploads, or active content. | Prevents formula injection, traversal, and active-content risks. |
| P7-D13 | Report status is `complete`, `complete_with_warnings`, or `incomplete`. Missing optional subsystems may be reported, but source-integrity failure, corrupt data, stale included results, non-finite values, or hash mismatch blocks generation. | Allows honest partial-project reporting without hiding critical defects. |
| P7-D14 | UI provides a report checklist/preview, format/section selection bounded by the canonical model, visible blockers, and Generate/Download. No engineering value is editable inside the report panel. | Reports reflect saved state rather than becoming another editor. |
| P7-D15 | Timestamps are ISO 8601 UTC. Tests inject a fixed clock and normalized ZIP timestamps so identical inputs/options are byte-identical; production generation time is an explicit fingerprint input. | Enables deterministic testing and audit trails. |

## In-scope work after separate implementation authorization

- Strict report preferences, manifest, section-status, validation-finding, and presentation-model contracts.
- Canonical report snapshot from one fully validated saved project without mutation.
- Report-input SHA-256 covering project/source identity, included user/calculated/recommended data, report options, generator/version, and generation time.
- Separate engineering KMZ containing selected current derived layers with prominent non-source/non-design labels.
- RFC 4180-compatible UTF-8 CSV schedules with stable columns/order and Excel-safe literal handling.
- XLSX workbook using the same canonical rows, stable sheet order, headings, filters, units, status/provenance columns, and accessible formatting.
- PDF summary with local vector overview, inventory/subsystem summaries, warnings/assumptions/limitations, validation status, source integrity, and manifest reference.
- Presentation-model JSON mirroring approved report sections, without PPTX rendering.
- Atomic package construction, per-member validation/hashes, final ZIP validation, cleanup, and download response.
- Typed frontend preview/generation/download workflow and production-rendered QA.
- Additive migration, generated schema/OpenAPI, full regression, source preservation, and independent QA/master/seal workflow.

## Explicit non-goals

- No changes to camera, lighting, Wi-Fi, or CAP engineering algorithms, constraints, recommendations, or accepted results.
- No automatic calculation, correction, completion, approval, or inference during report generation.
- No source upload, source pole, coordinate, edit, runtime-project, or accepted updated-KML mutation.
- No verified RF, photometric-reference, performance, availability, compliance, professional, installation, or optimality claim.
- No pole/CAP-site generation or movement; no proposed-layout mode.
- No email, cloud upload, sharing service, external template service, office automation, database, queue, or telemetry.
- No PPTX, construction drawing, procurement/BOM approval, permitting package, or signed/sealed engineering deliverable.
- No post-roadmap improvements or unrelated fixes; those follow closure under separately authorized scopes.

## Recovery protocol

1. Preserve worktree, output, isolated temporary location, and last valid milestone.
2. Never return or commit output from a failed generator.
3. Remove only an exact resolved isolated report-temp directory after validation.
4. Re-run affected formats, cross-format checks, final suite, and rendered workflow after generator/model changes.
5. Dependency, font, locale, ZIP timestamp, PDF rendering, lock, path, browser-download, and temp failures are recoverable work.
6. Record three materially different safe recovery attempts before a blocker claim under `AGENTS.md`.
7. A required prior-phase algorithm change is outside scope and requires a separate correction decision.
